# 后端任务：知时页二十四节气案例扩充与接口联调

任务日期：2026-11-06。输入附件：《二十四节气-案例总表-最终版.xlsx》。本轮按**无图版**交付，照片后续独立补充。

## 一、目标与当前基础

请将素材表转换为可维护、可校验的案例数据，接入现有知时页，让用户选择任一节气后，能够按省份查看当地案例、打开详情及原文来源。

现有项目已经实现案例共享类型、Zod 校验、本地数据读取、案例列表和详情 API，以及前端节气/省份筛选、分页、详情展示。当前运行数据为 **7 条已核实 + 1 条待核验**，不需要重新开发这些基础接口。本轮重点是数据导入、修订合并、覆盖检查和真实接口联调。

### 本轮范围

- 完整接收 47 条素材，逐条记录归档及处理结果。
- 优先交付 24 条主选案例，目标为 24 节气均有可公开、可追溯的案例；候选案例经核实后也可以公开。
- 保持现有 V1.0 只读接口和前端兼容。
- 图片不是验收前置条件。先交付完整的文字、地域、节气关联与来源。

### 本轮不包含

新建管理后台、数据库迁移、图片上传/抓图服务、向量库、AI 工具注册及 AI 控制地图、四时页翻书、知时页视觉改版。这些应另开任务，避免阻塞本轮材料接入。

5. 新 ID 使用稳定英文小写与连字符，符合现有 schema；不要使用易变的 Excel 序号或单纯依靠“节气+标题”作为最终实体身份。同一实体可关联多个节气，后续标题可能修订。
6. 保留 24 节气的主选 `caseId` 配置及素材来源关系，放在独立编辑配置中。**本轮不改变列表 ASCII ID 排序，不给现有 strict 响应私自增加字段**；后续如需主选推荐卡，再同步扩展前后端协议。

本轮可继续使用已有本地 JSON 存储，无需因为接入 Excel 就引入数据库。

## 六、接口交付与兼容要求

### 列表与详情：沿用既有实现

`GET /api/cultural-cases`

- 继续接受 `solarTermId`、`provinceCode`、`category`、`keyword`、`offset`、`limit`，筛选条件取交集。
- 保持默认 `offset=0`、`limit=10`，最大 `limit=20`。
- 返回 `{ version: "1.0", items, total, offset, limit }`。
- 仅返回 verified；`total` 为分页前、审核后、筛选后的真实数量。
- 保持按 ID 的 ASCII 升序排序；空条件可列出全部公开案例，超出末页返回空数组。
- 合法但没有收录的省份/节气返回 200 空列表；不得用演示案例填充。

`GET /api/cultural-cases/[caseId]`

- 已核实案例返回 `{ version: "1.0", item }`；pending 和不存在的 ID 都返回现有 404 `CASE_NOT_FOUND`。
- 非法输入、内部错误继续使用现有错误结构与状态码。
- GET 无 DeepSeek 密钥依赖，保留 `Cache-Control: no-store`。

**不要新增一个重复的案例检索接口或统计接口。** 前端 `fetchProvinceCaseCounts` 已能按节气拉取全部分页并统计省份，当前数据量可直接复用。地图按实际公开案例显示收录情况，不要求每个省都有人为填充的案例。

图片后续补充仍以稳定 `caseId` 对应素材，不用标题猜文件名。当前 `imageUrl` 仅接受本站 `/images/` 路径，不需要扩大外部域名。图片来源、作者及使用条件随图片批次单独交付，届时再同步需要的展示字段。
