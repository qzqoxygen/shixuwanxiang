## 4. 稳定标识与公共类型

### 4.1 节气 ID

唯一依据为现有 `lib/solar-terms.ts`。不得改用中文名、英文名或带连字符的新 ID。

```typescript
export type SolarTermId =
  | "lichun" | "yushui" | "jingzhe" | "chunfen" | "qingming" | "guyu"
  | "lixia" | "xiaoman" | "mangzhong" | "xiazhi" | "xiaoshu" | "dashu"
  | "liqiu" | "chushu" | "bailu" | "qiufen" | "hanlu" | "shuangjiang"
  | "lidong" | "xiaoxue" | "daxue" | "dongzhi" | "xiaohan" | "dahan";

export type ProvinceCode = string;
export type CulturalCaseId = string;
export type CulturalCategory = "folk_custom" | "agriculture" | "craft" | "food" | "other";
```

实现时让运行时 ID 集合与上述类型来自同一份现有数据，或通过测试保证同步。清明、夏至、秋分、冬至分别是 `qingming`、`xiazhi`、`qiufen`、`dongzhi`。

### 4.2 地区与案例 ID

- 对外统一使用**六位数字的省级编码字符串**，例如浙江 `330000`、山东 `370000`；不得转成数字。
- 运行时必须同时验证格式与受支持地区白名单，不能只靠正则。地图供应数据采用其他 ID 时，在地图适配层转换，不改变对外协议。
- 地图接入交付物必须包含地区映射表（编码、名称、地图 feature ID），且正式案例中的编码必须能在映射中找到。首轮地图覆盖范围在地图数据选定时由团队确认，未覆盖地区不返回可执行高亮操作。
- 案例 ID 使用 1–64 个小写字母、数字或连字符，首字符为字母或数字；全库唯一、稳定、不可复用。`case-001` 仅说明格式，不代表已有真实案例。
- 省级编码、节气 ID、案例 ID 均区分大小写；不自动纠正模型提供的未知 ID。

## 5. 文化数据与来源

```typescript
export interface CulturalSource {
  title: string;
  url: string;
  publisher?: string;
}

export interface CulturalCase {
  id: CulturalCaseId;
  title: string;
  solarTermIds: SolarTermId[];
  provinceCode: ProvinceCode;
  provinceName: string;
  regionName: string;
  category: CulturalCategory;
  description: string;
  relationNote: string;
  sources: CulturalSource[];
  verificationStatus: "verified" | "pending";
  imageUrl?: string;
}

export type VerifiedCulturalCase = CulturalCase & { verificationStatus: "verified" };
```

数据校验要求：

- `title` 1–100、`provinceName` 和 `regionName` 1–100、`description` 1–2000、`relationNote` 1–1000 个 UTF-16 单元；字符串非空并去除首尾空白。
- `solarTermIds` 为 1–24 个唯一合法 ID；一条记录归属一个省级地区。跨省案例拆成可分别核实的地区记录，保留各自来源，不让客户端猜测归属。
- `sources` 为 1–5 项；每项 title 1–200、publisher（如提供）1–100、url 最长 2048，且只允许绝对 HTTP(S) URL。相同 URL 去重。格式合法不代表内容可信，仍需人工核查。
- `imageUrl` 可缺省；如提供，允许本站 `/images/` 路径或团队批准域名的 HTTPS 地址，最长 2048。展示前必须有对应版权记录。
- 正式 API、工具和地图仅返回 `verified`；待核查记录与不存在记录对公开调用都返回“未找到”，不得暴露待核查内容。
- `relationNote` 说明该案例与指定节气的资料依据，不能把普通地方习俗强行关联某个节气。来源缺失或关联未证实的记录不能标为 verified。
- 在 `docs/cultural-sources/` 按案例 ID 记录核查人、核查日期、访问日期、来源依据、图片/文本授权或使用限制。可用团队成员代号，不必公开个人信息。
- AI 只能读取公开案例，不能新增、修改或批准正式数据。首轮没有案例写入 API；不在服务端根据模型提供的 URL 抓取任意网页。

## 6. 案例只读 API：让地图独立于 AI 工作

以下接口**均待实现**，由后端与文化数据负责人共用一个经过验证的数据读取模块。手动地图不依赖聊天请求成功。

### 6.1 `GET /api/cultural-cases`

可选 query：`solarTermId`、`provinceCode`、`category`、`keyword`、`offset`、`limit`。

- 前三项使用第 4、5 节类型及白名单；keyword 为去除首尾空白后的 1–100 单元字符串，空白值视为不筛选。
- offset 为十进制非负安全整数，默认 0；limit 为十进制整数 1–20，默认 10。未知参数、同名参数重复、非法值返回 400 `INVALID_INPUT`。
- 所有提供的条件取交集；keyword 在 title、regionName、description、relationNote 上做大小写不敏感的字面子串匹配，不执行正则或语义检索。
- 只检索 verified；按案例 ID 的 ASCII 升序稳定排序，再分页。超出末页、没有匹配结果都返回 200 和空数组。

```typescript
export interface CaseListResponse {
  version: "1.0";
  items: VerifiedCulturalCase[];
  total: number; // 筛选后、分页前的总数
  offset: number;
  limit: number;
}
export interface CaseDetailResponse {
  version: "1.0";
  item: VerifiedCulturalCase;
}
```

### 6.2 `GET /api/cultural-cases/[caseId]`

合法且已核实的 ID 返回 200 `CaseDetailResponse`；格式非法返回 400 `INVALID_INPUT`；不存在或 pending 返回 404 `CASE_NOT_FOUND`。编码后的路径须先解码再验证，不能用参数拼接任意文件路径。

两个接口均返回 JSON。首轮采用 `Cache-Control: no-store`，无密钥依赖；失败使用第 10 节公共错误结构。客户端缓存只能保存已验证案例；上线新数据时必须重新验证案例与地图关系。

## 7. 地图状态、操作和竞态规则

```typescript
export interface CulturalMapState {
  selectedSolarTermId: SolarTermId | null;
  selectedProvinceCode: ProvinceCode | null;
  selectedCaseId: CulturalCaseId | null;
  highlightedProvinceCodes: ProvinceCode[];
}

export type MapAction =
  | { type: "SET_SOLAR_TERM"; payload: { solarTermId: SolarTermId } }
  | { type: "HIGHLIGHT_PROVINCES"; payload: { provinceCodes: ProvinceCode[] } }
  | { type: "OPEN_CULTURAL_CASE"; payload: { caseId: CulturalCaseId } };
```

初始状态为三个选择字段 null、高亮数组为空。React 统一管理状态，服务端返回意图，不能返回或执行任意脚本。

| 操作 | 确定的执行语义 |
| --- | --- |
| `SET_SOLAR_TERM` | 设置节气，并清空选中省份、案例和全部高亮；即使选择相同节气也清空。手动切换使用相同规则 |
| `HIGHLIGHT_PROVINCES` | 用去重后的列表**替换**全部高亮，不追加；空数组清空。保留当前选择。必须先选节气，每个地区必须有匹配当前节气的 verified 案例 |
| `OPEN_CULTURAL_CASE` | 必须先选节气；案例必须 verified 且属于当前节气。设置案例及其所属省份，并把该省加入已有高亮（去重）。不隐式切换节气 |

手动选择省份只接受受支持编码；变更省份时清空案例，保留节气与高亮，并查询该省/当前节气的案例。关闭详情只清空 selectedCaseId。手动操作不需要模型许可。

一批操作按数组顺序验证与执行，最多 8 条。后端从请求 context 构造临时状态（高亮初始为空），按工具执行顺序推进。前端从当前完整地图状态重放同一批操作。

**原子应用规则：** 后端仅在最终回答成功且所有拟返回操作合法时返回操作；前端先验证整个响应、操作序列与必要案例详情，再在一次状态更新中应用。如果任一步失败，整批操作不生效，保留用户当前地图，并显示独立的地图错误；不能执行一半。后端需要丢弃不一致批次时返回 502 `INVALID_MAP_ACTIONS`，不返回伪造成功结果。

**防止过期响应：** 前端维护不放入 API 的递增 `mapRevision` 和活动请求标识。发送聊天时记录 revision；任何手动地图变更、接受 AI 地图批次、清空会话、页面卸载均使旧批次失效。收到聊天响应后以及异步获取详情完成后都再次比较：

- 请求已取消、清空或不是活动请求：丢弃响应，不追加回答、不改地图。
- 仅地图 revision 已变化：可以显示该回答，但跳过其所有地图操作，提示“回答基于之前的地图选择，未应用地图操作”。
- 请求仍有效且 revision 一致：完整校验后原子应用，并递增 revision。

手动筛选引起的案例查询也须有独立的请求序号/取消机制，旧列表和详情不能覆盖新选择。首轮无需让后端保存会话或地图状态。

## 8. 真实 Function Calling 工具协议

### 8.1 参数和执行结果

所有参数都是 JSON 对象；拒绝未知字段、非法 ID、非预期类型及显式 null（除非另有声明）。工具参数由服务端 Zod schema 校验，不能只相信模型声明的 JSON Schema。所有工具只读数据或生成操作，没有持久副作用。

```typescript
export type ToolName =
  | "search_cultural_cases" | "show_cultural_map"
  | "highlight_regions" | "open_cultural_case";

export interface SearchCulturalCasesArgs {
  solarTermId?: SolarTermId;
  provinceCode?: ProvinceCode;
  category?: CulturalCategory;
  keyword?: string;
  offset?: number;
  limit?: number;
}
export interface ShowCulturalMapArgs { solarTermId: SolarTermId }
export interface HighlightRegionsArgs { provinceCodes: ProvinceCode[] }
export interface OpenCulturalCaseArgs { caseId: CulturalCaseId }

export interface SearchCulturalCasesResult { items: VerifiedCulturalCase[]; total: number; offset: number; limit: number }
export interface ShowCulturalMapResult { solarTermId: SolarTermId; mapActions: MapAction[] }
export interface HighlightRegionsResult { provinceCodes: ProvinceCode[]; mapActions: MapAction[] }
export interface OpenCulturalCaseResult { item: VerifiedCulturalCase; mapActions: MapAction[] }

export type ToolErrorCode =
  | "INVALID_TOOL_ARGUMENTS" | "UNKNOWN_TOOL" | "MAP_CONTEXT_REQUIRED"
  | "CASE_NOT_FOUND" | "CASE_CONTEXT_MISMATCH" | "REGION_HAS_NO_CASES"
  | "TOOL_TIMEOUT" | "TOOL_RESULT_TOO_LARGE" | "TOOL_FAILED";

export type ToolResult<T> =
  | { ok: true; result: T }
  | { ok: false; error: { code: ToolErrorCode; message: string } };
```

| 工具 | 执行要求 |
| --- | --- |
| `search_cultural_cases` | 参数、筛选、排序和分页与案例列表 API 一致，但 offset/limit 是 JSON 数字整数。不暗中补入 context；模型如需当前地图条件须显式传参。允许空参数查询已核实案例。无结果是 `ok:true`、items 空、total 0；不生成地图操作 |
| `show_cultural_map` | 检查合法节气，生成一条 SET_SOLAR_TERM 并推进临时状态；即使该节气没有案例也允许切换，不能捏造案例 |
| `highlight_regions` | 参数为最多 34 个唯一受支持省级编码，空数组合法。要求临时状态已选节气；逐项核实该节气有案例，否则整次工具失败 `REGION_HAS_NO_CASES`。生成一条替换高亮操作 |
| `open_cultural_case` | 要求临时状态已选节气。案例缺失或 pending 返回 CASE_NOT_FOUND；与节气不匹配返回 CASE_CONTEXT_MISMATCH。成功返回真实详情和一条 OPEN_CULTURAL_CASE |

未选节气时，后两个工具返回 MAP_CONTEXT_REQUIRED，不隐式猜测。未知工具名返回 UNKNOWN_TOOL。预期错误保留具体 code；异常实现细节统一转为 TOOL_FAILED，不能把敏感异常文本传给模型或浏览器。

### 8.2 调用循环与客户端结果汇总

1. 复用 `runChatAgent`，注册上述四个工具，向模型发送标准 function tools；保持非思考、非流式模式。工具定义和服务端校验约束必须一致。
2. 最多 2 轮工具执行，每轮最多 4 次；最后一次模型请求 `tool_choice: "none"`，最多 3 次模型请求。先校验整批 tool_calls 的类型、ID 唯一性和数量，再按数组顺序串行执行；超限批次不能部分执行。
3. 每个调用都生成对应 `role: "tool"` 和相同 tool_call_id 的 JSON `ToolResult`，然后让模型继续回答。依赖搜索结果的打开案例应在下一轮发起，不能猜测同轮尚未知的案例 ID。
4. 每个工具原始 arguments 最多 2000 个 UTF-16 单元；每次执行（含输出序列化）最多 5 秒，且服从整个聊天请求的 120 秒期限与取消信号；序列化后输出最多 100000 UTF-8 字节。超限返回相应工具错误，不保留该次工具生成的操作。
5. 服务端从经过校验的工具结果累积地图操作、来源和事件；不得从模型自然语言或任意 JSON 文本中提取并执行地图操作。现有仅返回 answer 的 runner 需扩展这部分能力。
6. 同一请求内发生任一工具错误，允许模型继续生成解释，但首轮采用保守策略：最终 200 响应的 mapActions 必须为空。保留成功检索得到的来源和完整工具事件；界面提示“部分工具未完成，地图未更新”。无检索结果不是工具错误。
7. 若模型请求、最终回答、循环约束或最终操作验证失败，整个聊天请求返回非 2xx 错误，不返回地图操作或伪造回答。工具事件中的 success 仅代表服务端执行成功，不等于浏览器已应用操作。

## 9. 聊天 API V1.0 与旧接口兼容

### 9.1 请求

`POST /api/chat`，`Content-Type: application/json`。首轮不使用 SSE/流式响应。

```typescript
export interface ChatMessage { role: "user" | "assistant"; content: string }
export interface ChatContext {
  solarTermId: SolarTermId | null;
  provinceCode: ProvinceCode | null;
  caseId: CulturalCaseId | null;
}
export interface ChatRequestV1 {
  version: "1.0";
  messages: ChatMessage[];
  context: ChatContext;
}
```

```json
{
  "version": "1.0",
  "messages": [{ "role": "user", "content": "带我看看冬至的地方文化" }],
  "context": { "solarTermId": "dongzhi", "provinceCode": null, "caseId": null }
}
```

- messages 为 1–11 条、奇数条，user 开始且结束，严格 user/assistant 交替；最多携带 5 轮历史加新问题。
- user content 为 1–1000、assistant 为 1–8000 个 UTF-16 单元；长度按去空白前检查，去首尾空白后不得为空。重建消息对象，只允许 role/content。
- 请求正文最多 200000 UTF-8 字节，不信任 Content-Length。保留现有内容类型、JSON、来源、超时及取消检查。
- context 必须存在且三个字段齐全；没有选择用 null。仅有省份而无节气是合法地图状态；有 caseId 时必须同时有节气、省份，且案例已核实并与两者匹配，否则 400 INVALID_CONTEXT。
- root、context 与 message 的未知字段在 V1 中返回 INVALID_INPUT；不允许浏览器传 system、tool、模型配置或工具定义。合法 context 应作为结构化数据提供给 Agent，不允许拼接成可覆盖系统指令的内容。
- context 是不可信的客户端快照，必须重新验证；不能让模型自己修改服务端保存的“真实状态”，因为本阶段没有服务端会话状态。

### 9.2 成功响应

```typescript
export interface CulturalReference extends CulturalSource {
  caseId: CulturalCaseId;
  caseTitle: string;
}
export type ToolEvent =
  | { toolCallId: string; toolName: string; status: "success" }
  | { toolCallId: string; toolName: string; status: "error"; error: { code: ToolErrorCode; message: string } };
export interface ChatSuccessV1 {
  version: "1.0";
  reply: string;
  truncated: boolean;
  mapActions: MapAction[];
  references: CulturalReference[];
  toolEvents: ToolEvent[];
}
```

```json
{
  "version": "1.0",
  "reply": "已准备好冬至视图；文化案例以页面实际收录的数据为准。",
  "truncated": false,
  "mapActions": [{ "type": "SET_SOLAR_TERM", "payload": { "solarTermId": "dongzhi" } }],
  "references": [],
  "toolEvents": [{ "toolCallId": "call-example-1", "toolName": "show_cultural_map", "status": "success" }]
}
```

该示例只说明结构，不代表当前系统已调用工具或已有冬至案例。

- 六个字段必须返回，即使数组为空。reply 非空，最多 8000 个 UTF-16 单元；模型 finish_reason 为 length 时 truncated=true，否则必须为 stop，异常终止视为失败。
- references 只来自本请求成功 search/open 工具实际返回的 verified 案例 sources；普通模型知识回答允许为空，但不得编造出处。该列表标为“本次检索资料”，不暗示逐句事实核验。
- 引用按工具执行顺序、案例顺序、来源顺序收集，按 `(caseId, url)` 去重，最多 20 项（超出保留前 20）。caseTitle/title/url/publisher 必须来自数据记录，不由模型重写。
- toolEvents 按实际执行顺序返回，最多 8 项；toolCallId 与调用一一对应，长度 1–200。toolName 使用 string 以便记录 UNKNOWN_TOOL，模型给出的名称超过 64 单元视为 INVALID_TOOL_RESPONSE，不能直接写日志或插入 HTML。不暴露原始参数、思考过程或内部异常。
- V1 成功响应不混入旧 answer 字段。前端必须验证版本、reply、数组、事件和操作形状；未知版本/未知操作拒绝应用地图，不静默忽略。
- ChatPanel 的最近 5 轮记忆、加载、停止、重试与真实错误提示需要保留；显示纯文本，不执行模型返回的 HTML/脚本。

### 9.3 兼容与上线顺序

| 请求 | 升级后服务端行为 |
| --- | --- |
| JSON 对象完全没有 version 字段 | 旧模式：沿用现有消息校验和 `{answer, truncated}` 成功响应；不启用文化工具，不生成地图操作，避免旧客户端发生不可见操作 |
| version 为字符串 `"1.0"` | 严格验证 ChatRequestV1，使用新响应与业务工具 |
| version 存在但值不是 `"1.0"`（含 null/数字） | 400 UNSUPPORTED_VERSION；不能静默退回旧聊天 |

**当前基线还没有上述版本分流**，不能先让新前端发送 V1 请求并假定服务器已经支持它。

先完成并测试后端双模式兼容，再将 ChatPanel 切到 V1，并将地图状态由共同父组件或明确共享状态传入。新前端收到无版本旧成功响应必须明确提示协议不匹配，不能假装完成地图动作。全体客户端迁移且测试通过后，另行约定旧模式退役；本次不删除旧模式。

## 10. 错误、限制与安全

为使无法解析正文时也有统一错误格式，升级后的聊天和案例 API 使用同一种非 2xx 响应；保留两个旧字段供现有客户端兼容：

```typescript
export interface ApiFailure {
  version: "1.0";
  answer: null;       // 兼容字段，不是 AI 回答
  truncated: false;   // 兼容字段
  error: { code: string; message: string };
}
```

```json
{
  "version": "1.0",
  "answer": null,
  "truncated": false,
  "error": { "code": "NETWORK_ERROR", "message": "暂时无法连接 AI 服务，请稍后重试。" }
}
```

| HTTP | code | 含义 |
| --- | --- | --- |
| 400 | INVALID_JSON / INVALID_INPUT / INVALID_CONTEXT / UNSUPPORTED_VERSION | JSON、字段、上下文、版本无效 |
| 403 | INVALID_ORIGIN | 来源检查不通过 |
| 404 | CASE_NOT_FOUND | 案例 GET 不存在或不可公开；工具内同名错误按 ToolResult 回传 |
| 408 | CANCELLED | 请求取消（连接已断开时客户端可能收不到响应） |
| 413 | BODY_TOO_LARGE | 请求正文超限 |
| 415 | INVALID_CONTENT_TYPE | 聊天请求不是 application/json |
| 402 | INSUFFICIENT_BALANCE | 模型服务账户额度不足 |
| 429 | RATE_LIMITED | 上游限流或本应用限流；如有可信等待秒数，返回 Retry-After |
| 503 | API_KEY_MISSING / API_KEY_INVALID / ACCESS_DENIED | 服务端凭据未配置、无效或账户无权调用 |
| 504 | TIMEOUT | 上游请求或整次聊天超时 |
| 502 | NETWORK_ERROR / PROVIDER_REQUEST_ERROR / PROVIDER_UNAVAILABLE | 连接失败、上游拒绝模型参数、上游不可用 |
| 502 | INVALID_RESPONSE / TOOLS_UNAVAILABLE / INVALID_TOOL_RESPONSE / TOO_MANY_TOOL_CALLS / TOOL_ROUND_LIMIT / INVALID_MAP_ACTIONS | 模型、工具循环或最终操作不符合约定 |
| 500 | INTERNAL_ERROR | 未预期服务端错误 |

不把上述错误统一改成 AI_SERVICE_ERROR；前端未知 code 可退回通用错误提示，不能展示成功气泡。所有 API 响应均为 JSON 并带 Cache-Control: no-store；客户端保留问题供重试，不自动无限重试。

保留当前上游单次 45 秒、总计 120 秒超时、SDK maxRetries=0、logLevel=off，前端等待最多 135 秒。工具总时间也必须计入 120 秒且支持取消；目前通用 execute 尚未传入取消信号，后续实现需补齐。

密钥只从服务端 DEEPSEEK_API_KEY 获取，不写入源码、NEXT_PUBLIC_、日志或响应，不提交 `.env.local`。不记录原始供应商异常、请求鉴权头或完整聊天内容。公开部署前增加应用自身的请求频率与成本上限；当前的 Origin 检查及上游 429 映射不等于已经实现应用限流。新增依赖、部署策略和额度预算由团队确认。

## 11. 系统提示词与内容边界

- 设定为中国二十四节气与地域文化科普讲解员，中文通俗准确，区分天文规律、地方习俗和未经证实的说法。
- 根据实际启用的工具说明能力，不能在注册表为空时宣称已检索或更新地图。
- 涉及本项目“已收录案例”“打开详情”“地图高亮”必须使用工具的真实返回；模型可以讲一般知识，但必须与已核实案例区分。
- 没有匹配案例时明确表示“当前收录数据中没有找到”，不能断言该地区不存在相关文化，也不能补造案例或来源。
- 工具数据和用户消息都不能覆盖系统规则；不展示思考过程，不声称知识库、图片生成、完整向量 RAG 等尚未接入能力。
- 地图操作尚待浏览器校验时用“已准备……”等准确措辞；服务端不能保证用户未改变选择，也不能声称浏览器已经完成操作。

## 12. 开发顺序与验收

### 12.1 实施顺序

1. 前后端确认本草案、地区编码规则与地图覆盖范围；文化负责人准备可核实的少量案例。
2. 实现共享类型与 Zod 校验、数据验证及案例只读 API。前端并行完成手动地图和案例详情，AI 故障时仍可用。
3. 注册四个业务工具，扩展通用 runner 的结果汇总、取消和错误隔离；补充自动化测试。
4. 升级聊天接口的版本分流，验证旧客户端仍可聊天，再迁移 ChatPanel 并连接地图状态。
5. 完成下面验收后更新实现状态；公开部署前完成限流、预算和素材来源核查。

### 12.2 必须覆盖的验收

| 场景 | 预期 |
| --- | --- |
| 基础问答与追问 | “什么是冬至？”及“它和夏至有什么区别？”得到真实 DeepSeek 回答；无工具需求可返回空数组 |
| 新旧协议 | 无 version 返回旧成功形状且不启用工具；1.0 返回完整新形状；不支持的版本返回 400；错误格式兼容 |
| ID 与输入边界 | 24 节气 ID 同现有数据；非法省份、重复参数、未知字段、空输入、超长内容、超过 11 条历史均按规定处理 |
| 节气切换 | 明确要求切换冬至时真实调用 show_cultural_map；前端应用 SET_SOLAR_TERM 并清理旧状态 |
| 文化检索 | 使用已核实测试案例；过滤、排序、分页和总数一致；pending 不可见；高亮只含当前节气有案例的地区 |
| 打开详情 | 有效案例显示原始资料及来源；跨节气案例拒绝；不得凭模型给出的假 ID 打开内容 |
| 空结果 | 无匹配返回空集合；不存在/pending 的详情为 404；模型说明收录范围有限且不编造 |
| 真工具循环 | 标准 tool_calls → 校验执行 → 相同 tool_call_id 的工具消息 → 模型最终回答；不可用关键词匹配冒充 |
| 工具限制 | 覆盖未知工具、非法参数、重复调用 ID、轮次/数量/时间/输出大小超限；失败不泄漏内部信息 |
| 引用与事件 | 只来自真实执行结果，符合去重和数量规则；工具部分失败时所有地图操作为空 |
| 操作原子性 | 多操作按顺序应用；未知操作、缺失案例或非法批次全部拒绝，原地图不受部分操作影响 |
| 状态竞态 | AI 等待中手动切换、详情加载中切换、清空、取消以及旧列表晚返回，均不覆盖新状态 |
| 服务异常 | 缺密钥、余额不足、上游限流、网络失败、超时均有明确提示；手动地图及案例 API 仍可用 |
| 内容与素材 | 案例有可核查来源、节气关联依据和版权记录；AI 不写入正式案例库 |

测试沿用项目的 Node test runner，不为首轮额外引入测试框架。保留旧行为测试，并分别测试旧模式无工具、新模式有工具；基线里针对空 CULTURE_TOOLS 的断言需要随迁移调整，不能只删除断言让测试通过。

自动测试使用隔离的模型与网络响应，不访问真实密钥或消耗额度；真实 DeepSeek 与浏览器验收另列结果。可运行已有 TypeScript、ESLint、测试与构建检查，但通过这些检查不代表地图业务已验收。
